# 步骤 10：查找依赖项

在 C/C++ 软件开发中，管理构建依赖项始终是现代开发者面临的最具挑战性的问题之一。CMake 提供了广泛的工具集来发现和验证各种依赖项。

然而，对于正确打包的项目，无需使用这些高级工具。如今许多流行的库和工具项目都会生成正确的安装树，就像我们在步骤 9 中设置的那样，易于集成到 CMake 中。

在这种最佳情况下，我们只需要 `find_package()` 将依赖项导入我们的项目。

## 背景

用于通过 CMake 发现依赖项的五个主要命令，前四个是：

- **find_file()**：查找并报告命名文件的完整路径，这通常是 find 命令中最灵活的。
- **find_library()**：查找并报告静态归档文件或共享对象的完整路径，适合与 target_link_libraries() 一起使用。
- **find_path()**：查找并报告包含文件的目录的完整路径。这通常与 target_include_directories() 一起用于头文件。
- **find_program()**：查找并报告程序的可调用名称或路径。通常与 execute_process() 或 add_custom_command() 一起使用。

这些命令应被视为"备份"，在主 find 命令不适用时使用。主要的 find 命令是 `find_package()`。它使用全面的内置启发式方法和上游提供的打包文件，为请求的依赖项提供最佳接口。

## 练习 1 - 使用 find_package()

`find_package()` 使用的搜索路径和行为在其文档中有完整描述，但过于冗长，无法在此复制。只需说它搜索知名、不太知名、晦涩和用户提供的各种位置，试图找到符合给定要求的包。

```cmake
find_package(ForeignLibrary)
```

使用 `find_package()` 的最佳方式是确保所有依赖项都已安装到单个安装树中，然后通过 `CMAKE_PREFIX_PATH` 变量将该安装树的位置告知 `find_package()`。

> **注意** 构建和安装依赖项本身可能是一项艰巨的工作。虽然本教程会为此进行演示，但强烈建议使用包管理器进行项目本地依赖管理。
>
> `find_package()` 除了要查找的包之外，还接受几个参数。最值得注意的是：
>
> - 位置参数 `<version>`，用于描述要与包的配置版本文件进行比较的版本。应谨慎使用，最好通过包管理器控制要安装的依赖项版本，而不是可能在无害的版本更新上破坏构建。
> - 如果已知包依赖于依赖项的旧版本，使用版本要求可能是合适的。
> - `REQUIRED` 用于非可选依赖项，如果未找到则中止构建。
> - `QUIET` 用于可选依赖项，如果未找到则不向用户报告任何内容。
>
> `find_package()` 通过 `<PackageName>_FOUND` 变量报告其结果，对于找到和未找到的包将分别设置为 true 或 false 值。

## 练习 2 - 传递依赖项

库通常建立在彼此之上。多媒体应用程序可能依赖于提供对各种容器格式支持的库，该库又可能依赖于一个或多个其他库来实现压缩算法。

我们需要在我们放置在安装树中的包配置文件中表达这些传递需求。我们通过 CMakeFindDependencyMacro 模块来实现，该模块为已安装包的递归相互发现提供安全机制。

```cmake
include(CMakeFindDependencyMacro)
find_dependency(zlib)
```

`find_dependency()` 也会将参数从上层的 `find_package()` 调用转发。如果对 `find_package()` 使用 QUIET 或 REQUIRED 调用，`find_dependency()` 也会使用 QUIET 和/或 REQUIRED。

## 练习 3 - 查找其他类型的文件

在一个理想的世界中，我们关心的每个依赖项都会正确打包，或者至少有其他开发者为我们编写了发现它的模块。我们不生活在理想世界，有时我们必须亲自动手手动发现构建需求。

为此我们有本步骤前面枚举的其他 find 命令，如 find_path()。

```cmake
find_path(PackageIncludeFolder Package.h REQUIRED
  PATH_SUFFIXES
    Package
)
target_include_directories(MyApp
  PRIVATE
    ${PackageIncludeFolder}
)
```
