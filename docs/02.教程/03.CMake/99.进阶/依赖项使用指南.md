## 介绍

项目经常依赖其他项目、资产和产物。CMake 提供了多种将此类内容集成到构建中的方式。项目用户可以选择最适合需求的方法。

主要方法包括 `find_package()` 命令和 FetchContent 模块。FindPkgConfig 模块有时也会使用，但其集成度不如前两者，本指南不再进一步讨论。

依赖项也可以通过自定义依赖提供者提供。这可能是第三方包管理器，也可能是开发者实现的自定义代码。依赖提供者与上述主要方法协作，以扩展其灵活性。

## 使用 find_package() 获取预构建包

项目所需的包可能已经构建好，并存在于用户系统的某个位置。该包可能由 CMake 构建，也可能使用完全不同的构建系统构建。它甚至可能只是一组根本不需要构建的文件集合。CMake 为这些场景提供了 `find_package()` 命令。它在已知位置搜索，以及项目或用户提供的额外提示和路径。它还支持包组件和可选包。提供结果变量，允许项目根据是否找到包或特定组件来自定义其行为。

在大多数情况下，项目应使用基本签名。大多数时候，这只涉及包名称、可能还有版本约束，如果依赖项不是可选的则加上 REQUIRED 关键字。还可以指定一组包组件。

### find_package() 基本签名示例

```cmake
find_package(Catch2)
find_package(GTest REQUIRED)
find_package(Boost 1.79 COMPONENTS date_time)
```

`find_package()` 命令支持两种主要的搜索方法：

**Config 模式**
通过此方法，命令查找通常由包本身提供的文件。这是两种方法中更可靠的一种，因为包详细信息应与包保持同步。

**模块模式**
并非所有包都是 CMake 感知的。许多包不提供支持 config 模式所需的文件。对于此类情况，可以单独提供 Find 模块文件，由项目或 CMake 提供。Find 模块通常是知道包通常提供什么以及如何向项目展示该包的启发式实现。由于 Find 模块通常与包分开分发，它们不太可靠。它们通常单独维护，可能遵循不同的发布周期，因此容易过时。

根据使用的参数，`find_package()` 可能使用上述一种或两种方法。通过限制选项仅使用基本签名，config 模式和模块模式都可以用于满足依赖项。其他选项的存在可能将调用限制为仅使用两种方法之一，可能降低命令找到依赖项的能力。有关此复杂主题的完整详细信息，请参阅 `find_package()` 文档。

对于两种搜索方法，用户也可以在 cmake(1) 命令行或 ccmake(1) 或 cmake-gui(1) UI 工具中设置缓存变量来影响和覆盖包的查找位置。有关如何设置缓存变量的更多信息，请参阅用户交互指南。

### Config-file 包

第三方提供可执行文件、库、头文件和其他文件供 CMake 使用的首选方式是提供 config 文件。这些是与包一起分发的文本文件，定义 CMake 目标、变量、命令等。config 文件是普通的 CMake 脚本，由 `find_package()` 命令读取。

config 文件通常可以在名称匹配 `lib/cmake/`&lt;PackageName&gt;` 模式的目录中找到，但它们也可能在其他位置（参见 Config 模式搜索过程）。`&lt;PackageName&gt;` 通常是 `find_package()` 命令的第一个参数，甚至可能只是唯一的参数。也可以使用 NAMES 选项指定替代名称：

```cmake
find_package(SomeThing
  NAMES
    SameThingOtherName   # 包的另一个名称
    SomeThing            # 仍然查找其规范名称
)
```

config 文件的命名必须是 `&lt;PackageName&gt;`Config.cmake` 或 `&lt;LowercasePackageName&gt;`-config.cmake`（本指南其余部分使用前者，但两者都支持）。同一目录中可能还存在一个名为 `&lt;PackageName&gt;`ConfigVersion.cmake` 或 `&lt;LowercasePackageName&gt;`-config-version.cmake` 的可选文件。此文件用于 CMake 确定包版本是否满足 `find_package()` 调用中包含的任何版本约束。即使存在 `&lt;PackageName&gt;`ConfigVersion.cmake` 文件，调用 `find_package()` 时指定版本也是可选的。

如果找到 `&lt;PackageName&gt;`Config.cmake` 文件且满足任何版本约束，`find_package()` 命令认为找到了该包，并假设整个包按设计是完整的。

可能还有提供 CMake 命令或导入目标的其他文件供你使用。CMake 对这些文件没有强制任何命名约定。它们通过 CMake 的 `include()` 命令与主要的 `&lt;PackageName&gt;`Config.cmake` 文件相关联。`&lt;PackageName&gt;`Config.cmake` 文件通常会为你 include 这些文件，因此除调用 `find_package()` 外通常不需要任何其他步骤。

如果包的位置在 CMake 已知的目录中，`find_package()` 调用应该成功。CMake 已知的目录是特定于平台的。例如，使用标准系统包管理器在 Linux 上安装的包将自动在 /usr 前缀中找到。在 Windows 上安装在 Program Files 中的包也会自动找到。

如果包位于 CMake 不知道的位置（如 /opt/mylib 或 $HOME/dev/prefix），则无法自动找到。这是正常情况，CMake 提供了多种让用户指定此类库位置的方式。

调用 CMake 时可以设置 `CMAKE_PREFIX_PATH` 变量。它被视为要搜索 config 文件的基路径列表。安装在 /opt/somepackage 的包通常会安装如下 config 文件：/opt/somepackage/lib/cmake/somePackage/SomePackageConfig.cmake。在这种情况下，应将 /opt/somepackage 添加到 CMAKE_PREFIX_PATH。

环境变量 CMAKE_PREFIX_PATH 也可以填充要搜索的前缀。与 PATH 环境变量类似，这是一个列表，但需要使用特定于平台的环境变量列表项分隔符（Unix 上使用 `:`，Windows 上使用 `;`）。

CMAKE_PREFIX_PATH 变量在需要指定多个前缀或多个包在相同前缀下可用时提供便利。也可以通过设置匹配 `&lt;PackageName&gt;`_DIR` 的变量来指定包路径，例如 SomePackage_DIR。注意这不是前缀，而应该是包含 config 风格包文件的目录的完整路径，例如上述示例中的 /opt/somepackage/lib/cmake/SomePackage。有关其他可能影响搜索的 CMake 变量和环境变量，请参阅 `find_package()` 文档。

### Find 模块文件

不提供 config 文件的包仍然可以使用 `find_package()` 命令找到，如果有 FindSomePackage.cmake 文件可用的话。这些 Find 模块文件与 config 文件不同：

- Find 模块文件不应由包本身提供。
- Find`&lt;PackageName&gt;`.cmake 文件的可用性并不表示包或其任何特定部分的可用性。
- CMake 不会在 CMAKE_PREFIX_PATH 变量指定的位置搜索 Find`&lt;PackageName&gt;`.cmake 文件。相反，CMake 在 CMAKE_MODULE_PATH 变量给定的位置搜索此类文件。用户在运行 CMake 时设置 CMAKE_MODULE_PATH 是很常见的，CMake 项目追加到 CMAKE_MODULE_PATH 以允许使用本地 Find 模块文件也是很常见的。
- CMake 为一些第三方包提供了 Find`&lt;PackageName&gt;`.cmake 文件。这些文件是 CMake 的维护负担，这些文件落后于它们所关联的包的最新版本并不罕见。一般来说，不再向 CMake 添加新的 Find 模块。项目应鼓励上游包尽可能提供 config 文件。如果失败，项目应为其包提供自己的 Find 模块。

有关如何编写 Find 模块文件的详细讨论，请参阅 Find Modules。

### 导入目标

Config 文件和 Find 模块文件都可以定义导入目标。这些通常具有 SomePrefix::ThingName 形式的名称。当这些可用时，项目应优先使用它们，而不是可能提供的任何 CMake 变量。此类目标通常携带使用要求，并自动将头文件搜索路径、编译器定义等应用于链接到它们的其他目标（例如，使用 target_link_libraries()）。这比尝试使用变量手动应用相同内容更稳健且更方便。检查包或 Find 模块的文档以查看它定义了哪些导入目标（如果有的话）。

导入目标还应该封装任何特定于配置的路径。这包括二进制文件（库、可执行文件）的位置、编译器标志和任何与配置相关的数量。Find 模块在提供这些详细信息方面可能不如 config 文件可靠。

查找第三方包并使用其库的完整示例可能如下所示：

```cmake
cmake_minimum_required(VERSION 3.10)
project(MyExeProject VERSION 1.0.0)

# 使项目提供的 Find 模块可用
list(APPEND CMAKE_MODULE_PATH "${CMAKE_CURRENT_SOURCE_DIR}/cmake")

find_package(SomePackage REQUIRED)
add_executable(MyExe main.cpp)
target_link_libraries(MyExe PRIVATE SomePrefix::LibName)
```

注意，上述 `find_package()` 调用可以由 config 文件或 Find 模块解析。它仅使用基本签名支持的基本参数。例如，${CMAKE_CURRENT_SOURCE_DIR}/cmake 目录中的 FindSomePackage.cmake 文件将允许 `find_package()` 命令使用模块模式成功。如果不存在此类模块文件，系统将搜索 config 文件。

## 使用 FetchContent 从源码下载和构建

依赖项不一定需要预构建才能与 CMake 一起使用。它们可以作为主项目的一部分从源码构建。FetchContent 模块提供了下载内容（通常是源码，但可以是任何内容）并将依赖项添加到主项目中的功能（如果依赖项也使用 CMake）。依赖项的源码将与项目的其余部分一起构建，就像源码是项目自己的源码一部分一样。

一般模式是，项目首先声明它想要使用的所有依赖项，然后请求使它们可用。以下演示了该原则（更多示例参见 Examples）：

```cmake
include(FetchContent)
FetchContent_Declare(
  googletest
  GIT_REPOSITORY https://github.com/google/googletest.git
  GIT_TAG        703bd9caab50b139428cea1aaff9974ebee5742e # release-1.10.0
)
FetchContent_Declare(
  Catch2
  GIT_REPOSITORY https://github.com/catchorg/Catch2.git
  GIT_TAG        605a34765aa5d5ecbf476b4598a862ada971b0cc # v3.0.1
)
FetchContent_MakeAvailable(googletest Catch2)
```

支持各种下载方法，包括从 URL 下载和提取归档文件（支持一系列归档格式），以及包括 Git、Subversion 和 Mercurial 在内的多种存储库格式。还可以使用自定义下载、更新和补丁命令来支持任意用例。

当依赖项通过 FetchContent 添加到项目时，项目链接到依赖项的目标就像链接到项目的任何其他目标一样。如果依赖项提供 SomePrefix::ThingName 形式的命名目标，项目应链接到这些命名目标而不是非命名目标。看看为什么这是推荐的做法。

并非所有依赖项都可以通过这种方式引入项目。某些依赖项定义的目标名称与项目或其他依赖项中的其他目标冲突。通过 add_executable() 和 add_library() 创建的具体可执行和目标目标是全局的，因此整个构建中每个目标必须唯一。如果依赖项会添加冲突的目标名称，则不能通过此方法直接引入构建。

## FetchContent 与 find_package() 集成

&gt; 在版本 3.24 中添加。

某些依赖项支持通过 `find_package()` 或 FetchContent 添加。此类依赖项必须确保它们在已安装和从源码构建的场景中定义相同的命名目标。然后，消费项目链接到这些命名目标，并且只要项目不使用两种方法都不提供的其他内容，就可以透明地处理两种场景。

项目可以使用 FetchContent_Declare() 的 FIND_PACKAGE_ARGS 选项表示它愿意通过任何一种方法接受依赖项。这允许 FetchContent_MakeAvailable() 首先尝试通过调用 `find_package()` 来满足依赖项，使用 FIND_PACKAGE_ARGS 关键字后的参数（如果有的话）。如果这样没有找到依赖项，则如前所述从源码构建。

```cmake
include(FetchContent)
FetchContent_Declare(
  googletest
  GIT_REPOSITORY https://github.com/google/googletest.git
  GIT_TAG        703bd9caab50b139428cea1aaff9974ebee5742e # release-1.10.0
  FIND_PACKAGE_ARGS NAMES GTest
)
FetchContent_MakeAvailable(googletest)

add_executable(ThingUnitTest thing_ut.cpp)
target_link_libraries(ThingUnitTest GTest::gtest_main)
```

上述示例首先调用 `find_package(googletest NAMES GTest)`。CMake 提供了 FindGTest 模块，所以如果它在某个地方找到了已安装的 GTest 包，它将使其可用，并且依赖项不会从源码构建。如果未找到 GTest 包，则将从源码构建。无论哪种情况，都期望定义 GTest::gtest_main 目标，因此我们将单元测试可执行文件链接到该目标。

还可以通过 FETCHCONTENT_TRY_FIND_PACKAGE_MODE 变量获得高级控制。可以设置为 NEVER 以禁用所有到 find_package() 的重定向。可以设置为 ALWAYS 以尝试 find_package()，即使未指定 FIND_PACKAGE_ARGS（这应谨慎使用）。

项目也可能决定特定依赖项必须从源码构建。如果需要依赖项的修补或未发布版本，或者要满足要求所有依赖项从源码构建的某些策略，则可能需要这样做。项目可以通过向 FetchContent_Declare() 添加 OVERRIDE_FIND_PACKAGE 关键字来强制执行此操作。对该依赖项的 `find_package()` 调用然后将被重定向到 FetchContent_MakeAvailable()。

```cmake
include(FetchContent)
FetchContent_Declare(
  Catch2
  URL https://intranet.mycomp.com/vendored/Catch2_2.13.4_patched.tgz
  URL_HASH MD5=abc123...
  OVERRIDE_FIND_PACKAGE
)

# 以下自动重定向到 FetchContent_MakeAvailable(Catch2)
find_package(Catch2)
```

有关更高级的用例，请参阅 CMAKE_FIND_PACKAGE_REDIRECTS_DIR 变量。

## 依赖提供者

&gt; 在版本 3.24 中添加。

上一节讨论了项目可以用来指定其依赖项的技术。理想情况下，项目不应该真正关心依赖项来自哪里，只要它提供项目期望的内容（通常只是某些导入目标）。项目说明它需要什么，也可能指定从哪里获取它，在没有其他详细信息的情况下，以便它仍然可以开箱即用构建。

另一方面，开发者可能更感兴趣于控制依赖项如何提供给项目。你可能想使用自己构建的特定版本的包。你可能想使用第三方包管理器。你可能想将某些请求重定向到你控制的不同 URL，出于安全或性能原因。CMake 通过依赖提供者支持此类场景。

依赖提供者可以设置为拦截 `find_package()` 和 FetchContent_MakeAvailable() 调用。提供者有机会在回退到内置实现之前满足此类请求，如果提供者没有满足请求的话。

只能设置一个依赖提供者，并且只能在 CMake 运行早期非常特定的时间点设置。CMAKE_PROJECT_TOP_LEVEL_INCLUDES 变量列出了在处理第一个 project() 调用时将读取的 CMake 文件（仅该调用）。这是设置依赖提供者的唯一时间。整个项目中预计最多使用一个单独的提供者。

对于某些场景，用户不需要了解依赖提供者如何设置的详细信息。第三方可能提供一个文件，可以添加到 CMAKE_PROJECT_TOP_LEVEL_INCLUDES，这将在用户 behalf 设置依赖提供者。这是包管理器的推荐方法。开发者可以这样使用此类文件：

```bash
cmake -DCMAKE_PROJECT_TOP_LEVEL_INCLUDES=/path/to/package_manager/setup.cmake ...
```

有关如何实施你自己的自定义依赖提供者的详细信息，请参阅 cmake_language(SET_DEPENDENCY_PROVIDER) 命令。
