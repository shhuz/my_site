本教程的第一步旨在快速入门，学习如何用 CMake 为小型项目编写实用的构建配置。学完本节后，你将能够使用 CMake 描述可执行文件、库、源文件和头文件，以及它们之间的链接关系。

> **注意** 本教程的每个步骤都建立在前一步骤的基础上，但步骤之间并非严格连续。与学习 CMake 无关的代码（如 C++ 函数实现或超出教程范围的 CMake 代码）有时会在步骤之间添加。

## 背景

CMake 的典型使用围绕一个或多个名为 CMakeLists.txt 的文件展开。该文件有时被称为"列表文件"或"CML"。在给定的软件项目中，CMakeLists.txt 将存在于我们想要向 CMake 提供如何处理该目录或子目录中的文件和操作的指令的任何目录中。每个文件都由一组命令组成，描述与构建软件项目相关的某些信息或操作。

并非软件项目中的每个目录都需要 CML，但强烈建议项目根目录包含一个。这将作为 CMake 在配置期间初始设置的入口点。此根 CML 始终应在文件顶部或靠近顶部包含相同的两个命令：

```cmake
cmake_minimum_required(VERSION 3.23)

project(MyProjectName)

`cmake_minimum_required()` 是 CMake 向项目开发者提供的兼容性保证。调用时，它确保 CMake 将采用所列版本的行为。如果在包含上述代码的 CML 上调用更高版本的 CMake，其行为将完全等同于 CMake 3.23。

`project()` 命令是一个概念简单但功能复杂的命令。它告知 CMake 以下内容是对给定名称的独立软件项目的描述（而不是类似 shell 的脚本）。当 CMake 看到 `project()` 命令时，它会执行各种检查以确保环境适合构建软件，例如检查编译器和构建工具，以及发现主机和目标机器的字节序等属性。

> **注意** 虽然每个命令都提供了到完整文档的链接，但并不要求读者理解他们使用的每个 CMake 命令的完整语义。有效地学习 CMake（就像学习任何软件一样）是一个渐进的过程。

本教程步骤的其余部分将主要关注另外四个命令的用法：`add_executable()` 和 `add_library()` 命令用于描述软件项目想要产出的产物，`target_sources()` 命令用于将输入文件与其各自的输出产物关联，以及 `target_link_libraries()` 命令用于将输出产物彼此关联。

这四个命令是大多数 CMake 用法的骨干。正如我们将学到的，它们足以描述典型项目的多数需求。

## 练习 1 - 构建可执行文件

最基本的 CMake 项目是从单个源文件构建的可执行文件。对于这类简单项目，只需一个包含四个命令的 CMakeLists.txt 文件。

> **注意** 虽然 CMake 支持大写、小写和混合大小写的命令，但推荐使用小写命令，本教程将全程使用小写命令。

我们已经介绍的前两个命令是 `cmake_minimum_required()` 和 `project()`。在任何 CMake 使用中，根 CML 中的第一个命令始终是 `cmake_minimum_required()`。存在一些高级用法，其中 `project()` 可能不是 CML 中的第二个命令，但对于我们的目的而言，它始终是第二个命令。

我们需要了解的下一个命令是 `add_executable()`。此命令创建一个目标。在 CMake 术语中，目标是开发者用来命名一组属性的句柄。

目标可能想要跟踪的一些属性示例包括：
- 产物类型（可执行文件、库、头文件集合等）
- 源文件
- 包含目录
- 可执行文件或库的输出名称
- 依赖项
- 编译器和链接器标志

CMake 的机制通常最好理解为描述和操作目标及其属性。属性远不止这里列出的那些。CMake 命令的文档通常会讨论它们对所操作的 target 属性的功能。

目标本身只是名称，是这组属性的句柄。使用 `add_executable()` 命令就像指定我们要为目标使用的名称一样简单：

```cmake
add_executable(MyProgram)
```

现在我们已经有了目标的名称，我们可以开始将属性与之关联，比如我们要构建和链接的源文件。主要命令是 `target_sources()`，它接受目标名称作为参数，后跟一个或多个文件集合。

```cmake
target_sources(MyProgram
  PRIVATE
    main.cxx
)
```

> **注意** CMake 中的路径通常是绝对路径，或相对于 `CMAKE_CURRENT_SOURCE_DIR`。我们还没有讨论过这样的变量，所以你可以将其理解为"相对于当前 CML 的位置"。

每个文件集合都以作用域关键字为前缀。我们将讨论这些关键字的完整语义，但当我们将目标链接在一起时，快速解释是：这些关键字描述属性应如何被目标的依赖方继承。

通常，没有东西依赖于可执行文件。其他程序和库不需要链接到可执行文件，也不需要继承头文件或类似的内容。因此，此处适当的作用域是 `PRIVATE`，它告知 CMake 此属性仅属于 MyProgram 且不可继承。

> **注意** 这条规则几乎适用于所有情况。在高级和生僻用法之外，可执行文件的作用域关键字应始终为 PRIVATE。对于实现文件也是如此，无论目标是可执行文件还是库。唯一需要"看到" .cxx 文件的目标是构建它们的目标。

## 练习 2 - 构建库

我们只需要引入一个额外的命令来构建库：`add_library()`。它的工作方式与 `add_executable()` 完全相同，只是用于库。

```cmake
add_library(MyLibrary)
```

然而，现在是介绍头文件的好时机。头文件不直接作为翻译单元构建，也就是说它们不是构建要求。它们是使用要求。我们需要了解头文件，以便构建给定目标的其他部分。

因此，头文件的描述方式与 tutorial.cxx 等实现文件略有不同。它们也需要与我们之前使用的 `PRIVATE` 关键字不同的作用域关键字。

要描述头文件集合，我们将使用所谓的 `FILE_SET`。

```cmake
target_sources(MyLibrary
  PRIVATE
    library_implementation.cxx

  PUBLIC
    FILE_SET myHeaders
    TYPE HEADERS
    BASE_DIRS
      include
    FILES
      include/library_header.h
)
```

这很复杂，但我们逐点解释。首先，注意我们有实现文件作为 PRIVATE 源，与之前的可执行文件相同。然而，我们现在对头文件使用 PUBLIC。这允许库的使用者"看到"库的头文件。

> **注意** 我们还没有准备好讨论作用域关键字的完整语义。我们将在练习 3 中更完整地介绍它们。

作用域关键字之后是 `FILE_SET`，一组要作为单个单元描述的文件。FILE_SET 由以下部分组成：

- `FILE_SET <name>` 是 FILE_SET 的名称。这是我们可以在其他上下文中描述集合的句柄。
- `TYPE <type>` 是我们正在描述的文件类型。最常见的是头文件，但较新版本的 CMake 支持其他类型，如 C++20 模块。
- `BASE_DIRS` 是文件的"基础"位置。这最容易理解为编译器将通过 `-I` 标志进行头文件查找时描述的位置。
- `FILES` 是文件列表，与之前的实现源列表相同。

描述这么多信息很复杂，所以我们可以使用一些有用的快捷方式。值得注意的是，如果 FILE_SET 名称与类型相同，则无需提供 TYPE 字段。

```cmake
target_sources(MyLibrary
  PRIVATE
    library_implementation.cxx

  PUBLIC
    FILE_SET HEADERS
    BASE_DIRS
      include
    FILES
      include/library_header.h
)
```

我们可以采取其他快捷方式，但我们将在后面的步骤中讨论这些。

## 练习 3 - 链接库与可执行文件

我们准备好将库与可执行文件组合，为此我们必须引入一个新命令：`target_link_libraries()`。这个命令的名称可能有些误导，因为它做的远不止调用链接器。它描述目标之间的一般关系。

```cmake
target_link_libraries(MyProgram
  PRIVATE
    MyLibrary
)
```

我们终于准备好讨论作用域关键字了。有三个关键字：PRIVATE、INTERFACE 和 PUBLIC。它们描述属性如何向目标提供。

PRIVATE 属性（也称为"非接口"属性）仅对拥有它的那个目标可用，例如 PRIVATE 头文件仅对其附加的目标可见。

INTERFACE 属性仅对链接拥有目标的那些目标可用。拥有目标无法访问这些属性。纯头文件库是 INTERFACE 属性集合的一个例子，因为纯头文件库本身不构建任何内容，也不需要访问它们自己的文件。

PUBLIC 不是一种独立类型的属性，而是 PRIVATE 和 INTERFACE 属性的并集。因此，用 PUBLIC 描述的要求对拥有目标和消费目标都可用。

考虑以下具体示例：

```cmake
target_sources(MyLibrary
  PRIVATE
    FILE_SET internalOnlyHeaders
    TYPE HEADERS
    FILES
      InternalOnlyHeader.h

  INTERFACE
    FILE_SET consumerOnlyHeaders
    TYPE HEADERS
    FILES
      ConsumerOnlyHeader.h

  PUBLIC
    FILE_SET publicHeaders
    TYPE HEADERS
    FILES
      PublicHeader.h
)
```

> **注意** 我们在此处排除了每个文件集的 BASE_DIRS，这是另一个快捷方式。当省略时，BASE_DIRS 默认为当前源目录。

MyLibrary 目标有几个属性将在此 `target_sources()` 调用中被修改。到目前为止，我们笼统地使用了"属性"一词，但属性本身是可以推理的命名值。这里将修改的两个特定属性是 HEADER_SETS 和 INTERFACE_HEADER_SETS，它们都包含通过 target_sources() 添加的头文件集合列表。

值 internalOnlyHeaders 将添加到 HEADER_SETS，consumerOnlyHeaders 添加到 INTERFACE_HEADER_SETS，publicHeaders 将添加到两者。

当构建给定目标时，它将使用其自身的非接口属性（例如 HEADER_SETS），结合它链接的任何目标的接口属性（例如 INTERFACE_HEADER_SETS）。

> **注意** 不必以这种详细程度推理 CMake 属性。以上内容为完整性而描述。大多数时候你不需要担心命令正在修改的具体属性。

作用域关键字有一个与之关联的简单直觉，当从它们所应用的目标的角度考虑命令时：PRIVATE 是给我的，INTERFACE 是给别人的，PUBLIC 是给所有人的。

## 练习 4 - 子目录

随着我们进行教程，我们将添加更多命令来操作 Tutorial 可执行文件和 MathFunctions 库。我们希望确保将命令保持在与它们处理的文件本地。虽然对于像这样的小项目不是主要关注点，但对于具有许多目标和数千个文件的大型项目来说，这非常有用。

`add_subdirectory()` 命令允许我们合并位于项目子目录中的 CML。

```cmake
add_subdirectory(SubdirectoryName)
```

当子目录中的 CMakeLists.txt 被 CMake 处理时，子目录 CML 中描述的所有相对路径都是相对于该子目录，而不是顶层 CML。
