# 步骤 11：其他功能

CMake 有许多本教程未涵盖的功能，其中一些被认为是使用它们的项目的基本功能。其他功能在打包者中广泛使用，但在生产本地构建的软件开发人员中很少讨论。

此列表并非对 CMake 剩余能力的详尽讨论。它可能会随着时间的推移和重要性而变化。

## 练习 1：目标别名

本教程侧重于安装依赖项并从安装树中消费它们。它还建议使用包管理器来促进此过程。然而，出于历史和当代的各种原因，这并不总是 CMake 项目被消费的方式。

可以在父项目中完全将依赖项的源代码 vendor，并通过 `add_subdirectory()` 消费它。当执行此操作时，暴露的目标名称是在项目内部使用的那些名称，而不是通过 `install(EXPORT)` 导出的名称。目标名称将没有该命令前置到目标上的命名空间字符串。

某些项目希望支持与提供给 `find_package()` 使用者的接口一致的接口来支持此工作流。CMake 通过 `add_library(ALIAS)` 和 `add_executable(ALIAS)` 支持此功能。

add_library(MyLib INTERFACE)
add_library(MyProject::MyLib ALIAS MyLib)

## 练习 2：生成器表达式

生成器表达式是一种复杂的领域特定语言，在 CMake 的一些上下文中得到支持。最容易将它们理解为延迟求值的条件语句，它们表达需求，其中确定正确行为的输入在 CMake 配置阶段未知。

> **注意** 生成器表达式由此得名，它们在执行底层构建系统时求值。
>
> 生成器表达式通常与 `target_include_directories()` 结合使用，以表达构建和安装树中的包含目录需求，但文件集已取代了此用例。它们最常见的应用现在是在多配置生成器和复杂的依赖注入系统中。

```cmake
target_compile_definitions(MyApp PRIVATE "MYAPP_BUILD_CONFIG=$<CONFIG>")
```
