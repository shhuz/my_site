# 步骤 3：配置与缓存变量

CMake 项目通常有一些用户和打包者感兴趣的项目特定配置变量。CMake 有多种方式可以让调用用户或进程传达这些配置选择，但其中最基本的是 `-D` 标志。

在本节中，我们将探讨如何从 CML 中提供项目配置选项，以及如何调用 CMake 来利用 CMake 和各个项目提供的配置选项的内幕和外幕。

## 背景

如果我们有一个支持多种压缩算法的压缩软件 CMake 项目，我们可能希望让项目的打包者在他们构建我们的软件时决定启用哪些算法。我们可以通过消费通过 `-D` 标志设置的变量来实现这一点。

```cmake
if(COMPRESSION_SOFTWARE_USE_ZLIB)
  message("I will use Zlib!")
  # ...
endif()

if(COMPRESSION_SOFTWARE_USE_ZSTD)
  message("I will use Zstd!")
  # ...
endif()
```

```bash
cmake -B build \
    -DCOMPRESSION_SOFTWARE_USE_ZLIB=ON \
    -DCOMPRESSION_SOFTWARE_USE_ZSTD=OFF
...
I will use Zlib!
```

当然，我们希望为这些配置选择提供合理的默认值，以及传达给定选项用途的方式。此功能由 `option()` 命令提供。

```cmake
option(COMPRESSION_SOFTWARE_USE_ZLIB "Support Zlib compression" ON)
option(COMPRESSION_SOFTWARE_USE_ZSTD "Support Zstd compression" ON)

if(COMPRESSION_SOFTWARE_USE_ZLIB)
  # Same as before
# ...
cmake -B build \
    -DCOMPRESSION_SOFTWARE_USE_ZLIB=OFF
...
I will use Zstd!
```

通过 `-D` 标志和 `option()` 创建的名称不是普通变量，它们是缓存变量。缓存变量是全局可见的粘性变量，它们的值在最初设置后很难更改。实际上它们如此粘性，以至于在项目模式中，CMake 会在多次配置之间保存和恢复缓存变量。如果缓存变量被设置一次，它将保持不变，直到另一个 `-D` 标志抢占已保存的变量。

> **注意** CMake 本身有数十个用于配置的普通变量和缓存变量。这些在 cmake-variables(7) 中有文档说明，其运作方式与项目提供的配置变量相同。
>
> `set()` 也可用于操作缓存变量，但不会更改已经创建的变量。

```cmake
set(StickyCacheVariable "I will not change" CACHE STRING "")
set(StickyCacheVariable "Overwrite StickyCache" CACHE STRING "")

message("StickyCacheVariable: ${StickyCacheVariable}")
```

```bash
cmake -B build
...
StickyCacheVariable: I will not change
```

因为 `-D` 标志在任何项目命令之前处理，所以它们在设置缓存变量值方面具有优先权。

```bash
cmake -B build \
  -DStickyCacheVariable="Commandline always wins"
...
StickyCacheVariable: Commandline always wins
```

虽然缓存变量通常不能更改，但它们可以被普通变量遮蔽。我们可以通过将变量设置为与缓存变量相同的名称，然后使用 `unset()` 移除普通变量来观察这一点。

```cmake
set(ShadowVariable "In the shadows" CACHE STRING "")
set(ShadowVariable "Hiding the cache variable")
message("ShadowVariable: ${ShadowVariable}")

unset(ShadowVariable)
message("ShadowVariable: ${ShadowVariable}")
```

```bash
cmake -B build
...
ShadowVariable: Hiding the cache variable
ShadowVariable: In the shadows
```

> **注意** 脚本模式的运行方式略有不同，只有在命令中 `-P` 标志之前提供的 `-D` 标志才被评估并在运行脚本中可用。

我们现在可以重新配置项目。然而，这次我们要通过 `-D` 标志来控制配置。我们再次从导航到 Help/guide/tutorial/Step3 并调用 CMake 开始，但这次带上我们的配置选项。

```bash

```

构建后，我们应该观察到没有产生 Tutorial 可执行文件。因为缓存变量是粘性的，即使重新配置也不应该改变这一点，尽管是默认开启的选项。

```bash
cmake -B build
cmake --build build
```

不会产生 Tutorial 可执行文件，缓存变量已被"锁定"。要更改这一点，我们有两个选项。首先，我们可以编辑在 CMake 配置运行之间存储缓存变量的文件，即"CMake 缓存"。该文件是 build/CMakeCache.txt，在其中我们可以找到选项缓存变量。

```
//Build the Tutorial executable
TUTORIAL_BUILD_UTILITIES:BOOL=OFF
```

我们可以将其从 OFF 更改为 ON，重新运行构建，我们将获得 Tutorial 可执行文件。

> **注意** CMakeCache.txt 条目的形式为 `Name:Type=Value`，但"类型"只是一个提示。CMake 中的所有对象都是字符串，无论缓存怎么说。
>
> 或者，我们可以在命令行上更改缓存变量的值，因为命令行在 CMakeCache.txt 加载之前运行，其值优先于缓存文件中的值。

```bash
cmake -B build -DTUTORIAL_BUILD_UTILITIES=ON
cmake --build build
```

这样做我们观察到 CMakeCache.txt 中的值从 OFF 翻转为 ON，并且 Tutorial 可执行文件被构建。

## 练习 2 - CMAKE 变量

CMake 有几个重要的普通变量和缓存变量，用于允许打包者控制构建。诸如编译器、默认标志、包的搜索位置等决定都由 CMake 自己的配置变量控制。

其中最重要的是语言标准。由于语言标准可能对给定包呈现的 ABI 产生重大影响。例如，库在较新标准上使用标准 C++ 模板并在较早标准上提供 polyfill 是很常见的。如果在不同标准下消费库，则标准模板和 polyfill 之间的 ABI 不兼容可能导致无法理解的错误和运行时崩溃。

通过使用 `CMAKE_<LANG>_STANDARD` 缓存变量确保所有目标都在相同语言标准下构建。对于 C++，这是 `CMAKE_CXX_STANDARD`。

> **注意** 因为这些变量如此重要，所以开发者不在其 CML 中覆盖或遮蔽它们同样重要。如果在 CML 中遮蔽 `CMAKE_<LANG>_STANDARD`，因为库想要 C++20，而打包者已决定用 C++23 构建其余的库和应用程序，则可能导致上述可怕的、无法理解的错误。
>
> 没有非常充分的理由不要 `set()` CMAKE 全局变量。我们将在后面的步骤中讨论更好的方法，让目标传达定义和最低标准等需求。

在本练习中，我们将一些 C++20 代码引入我们的库和可执行文件，并通过设置适当的缓存变量用 C++20 构建它们。

## 练习 3 - CMakePresets.json

管理这些配置值可能很快就会变得令人不知所措。在 CI 系统中，将这些记录为给定 CI 步骤的一部分是合适的。例如，在 Github Actions CI 步骤中，我们可能会看到类似以下内容：

```yaml
- name: Configure and Build
  run: |
    cmake \
      -B build \
      -DCMAKE_BUILD_TYPE=Release \
      -DCMAKE_CXX_STANDARD=20 \
      -DCMAKE_CXX_EXTENSIONS=ON \
      -DTUTORIAL_BUILD_UTILITIES=OFF \
      # 可能有更多选项
      # ...

    cmake --build build
```

在本地开发代码时，即使只输入一次所有这些选项也可能容易出错。如果出于任何原因需要新的配置，多次这样做可能会很令人疲惫。

对此问题有许多不同的解决方案，你的选择最终取决于你作为开发者的偏好。面向 CLI 的开发者通常使用任务运行器以所需的选项调用 CMake 来构建项目。大多数 IDE 也有自定义机制来控制 CMake 配置。

在这里完全列举所有可能的配置工作流是不可能的。相反，我们将探索 CMake 的内置解决方案，称为 CMake 预设。预设为我们提供了一种命名和表达 CMake 配置选项集合的格式。

> **注意** 预设能够表达整个 CMake 工作流，从配置、构建到安装软件包。
>
> 它们比我们这里能涵盖的灵活得多。我们将仅限于使用它们进行配置。

CMake 预设来自两个标准文件：`CMakePresets.json`， intended to be a part of the project and tracked in source control；以及 `CMakeUserPresets.json`， intended for local user configuration and should not be tracked in source control。

对开发者有用的最简单预设无非就是配置变量。

```json
{
  "version": 4,
  "configurePresets": [
    {
      "name": "example-preset",
      "cacheVariables": {
        "EXAMPLE_FOO": "Bar",
        "EXAMPLE_QUX": "Baz"
      }
    }
  ]
}
```

在调用 CMake 时，以前我们会这样做：

```bash
cmake -B build -DEXAMPLE_FOO=Bar -DEXAMPLE_QUX=Baz
```

现在我们可以使用预设：

```bash
cmake -B build --preset example-preset
```

CMake 将搜索名为 CMakePresets.json 和 CMakeUserPresets.json 的文件，如果可用，则从它们加载命名的配置。

> **注意** 命令行标志可以与预设混合使用。命令行标志优先于预设中找到的值。
>
> **注意** 在 CMake 4.4 及更新版本中，CMake 还可以从 `cmake --presets-file` 指定的任何文件加载预设。当在多个项目之间重用设置时，这可能很有用，因为它避免了必须在每个项目的单独 CMakePresets.json 文件中复制它们。

预设还支持有限的宏，可以在预设内大括号展开的变量。我们感兴趣的唯一一个是 `${sourceDir}` 宏，它展开为项目的根目录。我们可以使用它来设置构建目录，在配置项目时跳过 `-B` 标志。

```json
{
  "name": "example-preset",
  "binaryDir": "${sourceDir}/build"
}
```
