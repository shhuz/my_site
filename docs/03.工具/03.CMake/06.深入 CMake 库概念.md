# 步骤 5：深入 CMake 库概念

虽然可执行文件大致通用，但库有各种不同的形式。有静态归档文件、共享对象、模块、对象库、纯头文件库，以及描述要由其他目标继承的高级 CMake 属性的库，仅举几例。

在本节中，你将了解 CMake 可以描述的许多最常见的库类型。这将涵盖 `add_library()` 在项目内部的大多数用法。从依赖项导入（或由项目导出以供消费为依赖项）的库将在后续步骤中涵盖。

## 背景

如我们在步骤 1 中所学，`add_library()` 命令接受要创建的库目标的名称作为其第一个参数。第二个参数是可选的 `<type>`，以下值有效：

- **STATIC**：静态库：用于链接其他目标的对象文件归档文件。
- **SHARED**：共享库：可由其他目标链接并在运行时加载的动态库。
- **MODULE**：模块库：可能不能被其他目标链接的插件，但可以使用类似 dlopen 的功能在运行时动态加载。
- **OBJECT**：对象库：尚未归档或链接到库的对象文件集合。
- **INTERFACE**：接口库：指定依赖项使用需求的库目标，但不编译源文件，也不在磁盘上生成库产物。

此外，还有从外部项目或模块导入到当前项目的 **IMPORTED** 库。我们将在后续步骤中简要介绍这些。

MODULE 库最常见于插件系统，或作为对 Python 或 Javascript 等运行时加载语言的扩展。它们的行为非常类似于普通共享库，只是它们不能被其他目标直接链接。它们足够相似，因此我们不会在这里更深入地介绍它们。

## 练习 1 - 静态库与共享库

虽然 `add_library()` 命令支持显式设置 STATIC 或 SHARED，并且这有时是必要的，但对于大多数可以作为任意一种的"普通"库，最好将第二个参数留空。

当未给定类型时，`add_library()` 将根据 `BUILD_SHARED_LIBS` 的值创建 STATIC 或 SHARED 库。如果 `BUILD_SHARED_LIBS` 为 true，则创建 SHARED 库，否则创建 STATIC 库。

```cmake
add_library(MyLib-static STATIC)
add_library(MyLib-shared SHARED)

# 取决于 BUILD_SHARED_LIBS
add_library(MyLib)
```

这是期望的行为，因为它允许打包者确定将生成什么类型的库，并确保依赖项链接到该版本的库而无需修改其源代码。在某些上下文中，完全静态构建是合适的，而在其他上下文中，共享库是可取的。

> **注意** CMake 默认不定义 BUILD_SHARED_LIBS 变量，这意味着没有项目或用户干预，`add_library()` 将生成 STATIC 库。
>
> 通过将 `add_library()` 的第二个参数留空，项目为其打包者和下游依赖项提供了额外的灵活性。

## 练习 2 - 接口库

接口库是仅向其他目标传达使用需求的库，它们不构建自身也不产生任何产物。因此，接口库的所有属性本身必须是接口属性，使用 INTERFACE 作用域关键字指定。

```cmake
add_library(MyInterface INTERFACE)
target_compile_definitions(MyInterface INTERFACE MYINTERFACE_COMPILE_DEF)
```

C++ 开发中最常见的接口库类型是纯头文件库。此类库不构建任何内容，仅提供发现其头文件所需的标志。

## 练习 3 - 对象库

对象库有几种高级用途，但也有一些难以在教程范围内完全列举的微妙之处。

```cmake
add_library(MyObjects OBJECT)
```

对象库最明显的缺点是对象本身不能传递链接。如果对象库出现在目标的 INTERFACE_LINK_LIBRARIES 中，链接该目标的依赖项将不会"看到"这些对象。对象库在这种上下文中将表现得像接口库。在一般情况下，对象库仅适合通过 `target_link_libraries()` 以 PRIVATE 或 PUBLIC 方式消费。

对象库的常见用例是将几个库目标合并到单个归档文件或共享库对象中。即使在单个项目中，库也可能因各种原因作为不同目标维护，例如属于组织内不同的团队。然而，可能希望将它们作为单个面向消费者的二进制文件分发。对象库使这成为可能。
